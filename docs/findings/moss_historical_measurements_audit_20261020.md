## 0. 一句话结论

8 条被回审断言：**2 条已推翻**（H1 卡归因、H3 卡级链路上限）、**5 条需加注**（H2/H4/H5/H7/H8）、**1 条成立**（H6）。
最要紧的两条改判：

1. **「另一块物理卡」是错的。** 2026-10-17 的 11.3386 s/步与今天的数据跑在**同一张卡**上（`GPU-bfda6d91-…`），3.87× 的差异来自 PCIe 协商宽度（×4 → ×16），而不是换了一张卡。今日同卡 ×4 下得 11.3443 s/步（512 幅面），与原值 11.3386 差 0.06%——**幅面不同、精度也不同**（今日 fp16，基线 bf16）而步时相同，正因为 swap20 每步固定搬 9.06 GB、步时由搬运决定（×4 下 DMA 占步时 96.9%），这同时排除了「换卡」与「算力差异」两种替代解释。
2. **「3.14 GB/s 就是这块卡的实际上限」不成立。** 链路宽度本身不是卡的常量：同一台机器三天内实测到 ×16 / ×8 / ×4，实测 H2D 0.755 → 1.476 → 2.90 GiB/s，与宽度严格成正比（每档 ×1.96）。

连带影响：P-C1（fp16 数值治理）应从「最高优先阻塞」**降级为「待硬件样本前不阻塞」**；P1 的 `P-C3`（×8 → ×16 诊断）应从「纯诊断」**升级为仅次于 P0 的性能项**——它对应 1.96× 的单点收益，是本机最大的一根杠杆。

## 3. 已推翻 · H1：11.3386 s/步 不是「另一块物理卡」

### 3.1 原断言（`moss_vs_kohakumoss_trainer_ab_20261019.md:231–241`）

原文把 2026-10-17 的 11.3386 s/步与 2026-10-18 的 2.9258–2.9312 s/步之间 3.87× 的差距归因为
「**最可能为另一块物理卡 + ×4 链路，属推断；不是口径差异**」，并列了三条证据：
① 基线 run 的 `environment.json` 记 `gpu_uuid = GPU-bfda6d91-…`，与当时在机的 `GPU-46c7d0db` 不是同一张；
② 同仓 `compare.md:30` 写「历史 x4 约 11.3 秒/步属于另一批运行，此次重插后链路/UUID/硬件状态改变」；
③ 算术 9.06 GB / 11.3386 s = 0.799 GB/s ≈ Gen1 ×4。

### 3.2 今日证据

| # | 证据 | 路径 |
| --- | --- | --- |
| 1 | 今日 A 轮跑在 `GPU-bfda6d91-279a-3ffa-93ce-b48c28bcfdfb` 上，**与 10-17 基线同一 UUID** | `output/analysis/moss-ab/512-ab/run-A2/env.json`、`run-A3/env.json` |
| 2 | 该轮 `hardware_note` 原文：「Same UUID as the 2026-10-17 run that measured 11.3386 s/step; this round reproduces 11.33 s/step at blocks_to_swap=20」 | 同上 |
| 3 | `cross_round.json` 的 `round_A2.formal_swap20 = 11.3443`、`swap20_steady = 11.332`；注意这是 **512 幅面**（run-A2 协议）的 swap20 正式轮，不是 256×256 | `512-ab/run-A3/cross_round.json` |
| 4 | 10-19 的机器上确实是 `GPU-46c7d0db`（该轮 `gpu_uuid` + `pcie_link_width_current = 8`） | `512-ab/run-A/env.json` |
| 5 | `environment.json` 的字段集合为 `repo / run_dir / gpu_uuid / gpu_name / compute_capability / gpu_total_memory_bytes / python / torch / cuda / source_commit / env / timing_scope / steps / excluded_initial_steps_for_hot_statistics`——**不含任何 pcie 字段，也不含功耗上限** | `output/runs/moss-image-bf16-baseline10-20261017-085341/environment.json` |

### 3.3 判定推理链

1. **「两块不同的卡」在 10-19 的机器状态下是真的**，所以原作者不是编的：那时在机的确是 `GPU-46c7d0db`（证据 4）。这一步不推翻。
2. **但把它写成归因结论就错了**：10-17 那张 `GPU-bfda6d91` 在 10-20 回到了机器里（证据 1），而同一台机器、同一 swap20、同一 ×4 链路下它给出 11.332–11.3443 s/步（证据 2、3），与 11.3386 相差 **0.06%**。
   这里必须写明一处**幅面差异**：基线是 256×256、A2 是 512 幅面。这不削弱结论，反而是第二重印证——swap20 每步固定搬 2×20×226.5 MB = 9.06 GB，与幅面无关；9.06 GB ÷ 0.799 GB/s ≈ 11.34 s。**幅面变了步时不变**，说明步时由搬运决定而非幅面/算力。同一张卡能给出同量级原值 ⇒ 「换卡」不是必需假设。
3. **「精度不同」这一替代解释也被排除**：基线 run 是 commit `975e14a8`，`train.log:133` 记 `unet dtype: torch.bfloat16`、`:84` 记 BF16 compute on sm_75（当时尚无 `precision_policy` 的 bf16→fp16 改写，该改写由后续提交引入）。而今日 `run-A2` 的 `effective_mixed_precision = fp16`。两者**精度路径不同、步时相同**，只可能因为步时在 ×4 下被 DMA 支配（`round_A2.dma_share_swap8_pct = 96.9`）。这同时给「步时 ≈ max(总DMA, 总计算)」模型补了一条独立支撑。
4. **剩下的唯一变量就是链路宽度**：10-17 15:15 的 nvidia-smi 采样是 `gen.current=1, gen.max=1, width.current=16, width.max=16`（`output/runs/moss-image-ab-pcie-x16-20261017-151444/bf16-attempt1/telemetry.jsonl:17` 与 `preflight-final.json` 的 gpu 行），今日 ×4 的 `run-A2` 与 ×8 的 `run-A3` 都在同一张卡上。**卡不变、宽度变，步时按 3.87× 变化** —— 归因应改为「同卡 + 不同链路宽度」。

### 3.4 结论与边界

- 判定：**已推翻**（作为「另一块物理卡」的归因）。原文「×4 链路」那半边是对的，且今日首次给出直接测量（`pcie_link_width_current = 4`、`h2d_gb_s = 0.755`、`block_h2d_ms = 279.5`）。
- 边界 1：10-17 基线的 `environment.json` 不记 pcie，**那次到底是不是 ×4 仍属 `[算术]` 推断**（9.06 GB / 11.3386 s = 0.799 GB/s 与今日 ×4 的 0.755 GiB/s 量级吻合，且今日同卡 ×4/swap20 落在 11.3443）。本文件比原文多的是「同卡可复现」，不是「基线链路宽度已实测」。
- 边界 2：`run-A2` 的功耗上限是 120 W（基线 run 未记录功耗上限）。今日 120 W 下复现原值这一事实，说明功耗差异**不参与**这 3.87×（否则时间会更长），但它也意味着「×4 + 225 W」这一组合未被测过。
- 落地建议（由后续任务执行，不在本任务）：在 `moss_vs_kohakumoss_trainer_ab_20261019.md` §7-4 末补一行指针
  「**2026-10-20 复核：卡归因已推翻，同卡不同链路宽度；见 `moss_historical_measurements_audit_20261020.md` §3。**」
  这一行是**追加勘误**，不改原文判定文字，符合「不改写历史文档」边界。

## 4. 需加注 · H2：fp16 的 NaN 是这张卡的事，不是 sm75 的事

### 4.1 原断言（`moss_vs_kohakumoss_trainer_ab_20261019.md:226–228`）

「**fp16 数值失败根因未定位**……第 6 步 CUDA 失败于 MOSS `q_norm` 调用处……Xid 31 MMU Fault（ENGINE CE2）。
**与生产 10 步 tier-hot 干净之间存在未解释的矛盾**——在矛盾解释之前，『fp16 可长训练』不能算已证。」

事件 d 的细节（这是「生产 10 步干净」的原始落盘）：`precision.mixed_precision = bf16`、`amp.scaler_present = False`、`updates.attempted = 10 / effective = 10 / skipped = 0`，`steps.csv` 10/10 `effective_update = True`，逐步 `avr_loss` 全部有限（0.0472 / 0.597 / 0.0483 / 0.0538 / 0.0517 / 0.0617 / 0.058 / 0.0414 / 0.0556 / 0.0509），`grep -ic nan train.log = 0`。

### 4.3 判定推理链

1. **a、b、c 三件事全在 `GPU-46c7d0db` 上**（证据 a 的 gpu 行、b 的 `gpu_uuid`、c 的 Xid 记录）。这张卡后来被 Xid 13 判死并换下。
2. **换卡后 fp16 有限**：e 两轮都是 `effective_mixed_precision = fp16`，步数跑满、loss 有限、adapter 每次 sha256 不同（说明权重真的在动）。d 那轮虽然走的是 bf16，同样 10/10 有限、0 NaN。
3. **「矛盾」因此有了解释**：不是「生产 10 步干净」与「FP16 臂全 NaN」互相打脸，而是**它们本来就不是同一张卡**。这与 H1 的服务同一条结论（同卡复现），但方向相反：H1 说的是「同卡能复现 11.33」，这里说的是「NaN 只出现在那张死卡上」。
4. **反证补强（卡级故障，而非 fp16 精度问题）**：`run-A` 里另有一段 `torch.float32` 诊断臂（`raw.log` 同时出现 `unet dtype: torch.float16` 与 `: torch.float32`），**fp32 仍然 NaN、步时约 19.82 s**。若 32 位浮点也不收敛/不有限，则问题不在 16 位精度，而在该卡的数字通路或内存通路。

### 4.4 允许的措辞与不允许的措辞

- 允许（建议替换原结论句）：
  「**fp16 的 NaN / Xid 31 与 `GPU-46c7d0db` 这张卡强相关，不能推广为『MOSS 在 sm75 上 fp16 训练不稳』；该卡已在 10-19 被 Xid 13 判死，换卡后的 fp16 轮次数值有限。**」
- **不允许**外推为「fp16 在 sm75 上已证安全」：样本只有 2 张卡，且机制未定位（不知道该卡的什么故障产生 NaN）。这条边界必须和结论一起写。
- **不允许**把今日 B 侧的 NaN 混进来：`run-B`（B 侧 `FP16_FIX = fp32_residual`）在 `GPU-bfda6d91` 上仍 13/20 NaN。这是 **B 侧 kernel 体系自身的问题**，与 A 的卡病理是两件事，混用会同时污染两条结论。
- 顺带纠一条上游前提：**「配置写 bf16 但 sm75 就地改写 fp16」对 baseline10 不成立**。那次 run 的 commit `975e14a8` 还没有 `library/training/precision_policy.py` 的改写逻辑，`train.log:133` 明确是 `torch.bfloat16`。它的干净不能用「其实是 fp16」解释，这反而是「bf16 在本卡能跑满 10 步」的唯一实测样本。

## 5. 已推翻 · H3：「3.14 GB/s 就是这块卡的实际上限」

### 5.1 原断言（`block_swap_restore_link_limit_50hx_20261019.md`）

- `:21` 小节标题即「链路天花板 3.14 GB/s」；
- `:25–30` 纯拷贝微基准表；
- `:34` 「3.14 GB/s 就是这块卡的实际上限」；
- `:49`（99.4% 链路利用率一行）；
- `:62` 「只在 CMP 50HX（**窄链路 3.14 GB/s**）上验证」。

### 5.2 今日证据：同一张卡、三档宽度、实测 H2D

| 链路宽度 | 实测 H2D | 每块 216 MiB 的耗时 | 落盘路径 |
| --- | ---: | ---: | --- |
| Gen1 ×16 | 2.796 / 2.905 / 2.908 GiB/s（128 MiB pinned，三次） | 约 73–76 ms | `output/runs/moss-image-ab-pcie-x16-20261017-151444/h2d.json`（每次 trial 后回读 `link_after_copy = …1, 1, 16, 16`） |
| Gen1 ×8 | 1.476 GiB/s | 142.9 ms | `512-ab/run-A3/env.json`（`pcie_link_width_current = 8`、`pcie_link_width_max = 16`） |
| Gen1 ×4 | 0.755 GiB/s | 279.5 ms | `512-ab/run-A2/env.json`（`pcie_link_width_current = 4`） |

比值：1.476 / 0.755 = **1.955**；2.905 / 1.476 = **1.968**。宽度每翻一倍，带宽翻一倍（扣 2–3% 效率）—— **带宽是链路状态的函数，不是卡的属性**。

旁证（同卡同轮训练内推导，`[算术]`）：`run-A3` 的 swap 拟合斜率 285.64 ms/块，每块双向 453 MB ÷ 0.28564 s = **1.586 GB/s**（=1.476 GiB/s）；`run-A2` 斜率 559.51 ms/块 ⇒ 453 MB ÷ 0.55951 = 0.810 GB/s（=0.754 GiB/s）。两条都与 `env.json` 的独立测量互洽。

### 5.3 判定推理链

1. 「3.14 GB/s」这个**量级**属于 ×16 状态，今日 ×16 落盘值 2.90 GiB/s 与之同档，不是错数。

## 8. 成立 · H6：次线性与「文本长度是显存主变量」仍然站得住

### 8.1 原断言（`moss_image_token_budget_tiers_20261017.md`）

- `:210–212` 「面积档位收益次线性（1024→768 1.65×、1024→512 1.87×），固定项约 2.1 s/step 占主导；文本长度是显存主变量」；
- `:202 / :203 / :206` 512-short 3.036、512-long 7.210、1024-swap28-long 14.120。

### 8.2 为什么判「成立」

1. **结构上被今日独立复现**：今日 A3 的 swap 扫描 8 / 12 / 16 / 20 → 2.4173 / 3.5535 / 4.7020 / 5.8430 s/步，线性拟合 0.1300 + 0.28564·swap，四点残差 +0.09% / −0.12% / +0.04% / 0.00%。这正是「**固定项（截距）+ 每换一块的线性代价**」的同构模型 —— 与原文「≈2.1 s 固定项 + 每 token 斜率」是同一族函数形式，而不是互相矛盾。
2. **「固定项主导」在小幅面下同样成立**：今日 A3 swap8 的 512 幅面步时 2.4173 s，其中 DMA 占 94.5%（`cross_round.json` 的 `dma_share_swap8_pct`），计算项很小 —— 与「降分辨率换不到等比例时间」一致。
3. **文本长度是显存主变量**：今日未测文本维度，但这条与其说是性能结论不如说是显存事实，且与 4096-token 只在 512 档装得下（原文 `:213`）一致，无反证。

### 8.3 唯一需标注

系数（2.1 s、0.00084 s/token）是 **swap20 @ ×16** 的。今日 ×8 的固定项是 0.1300 s + 每块 0.28564 s，不是同一组数。**不改正文**，只在使用这两条结论派生物理量时标注来源状态。

## 0. 一句话结论

在**同一张卡、同一份数据、同一幅面（512）**上，本轮首次拿到两侧都可用的端到端数字：
**A（krea2-webui）2.4181 s/step / 8992 MiB，B（KohakuMossTrainer，全 eager）12.0330 s/step / 2499 MiB**。
两侧步时都只由**同一条 PCIe 链路的搬运字节数**决定——A 每步搬 3.624 GB，B 每步搬 18.646 GB，
字节比 5.145 对上步时比 4.976（差 3.4%）；实测有效 H2D 带宽 A 1.4987 GB/s、B 1.5496 GB/s，
是同一条链路的两个读数。因此 B 的 4.98× 慢**不是算子实现问题，是搬运字节问题**；
而 B 的高性能 kernel 层在 sm75 上唯一被实测到的效果是**把一张 CMP 50HX 打到 Xid 154 永久退役**（§7）。
同时本轮把「2026-10-17 的 11.3386 s/步」这条悬案收口：
**同一张物理卡（UUID 相同），差异全部来自链路 ×4 → ×8，零残差**（§9）。

同一张卡（世代 3）在 09:20 重启之前的 ×4/120 W 段（run-A2，10-20 08:xx）**只作链路对照**：它的绝对值按 protocol.md §0.1b 作废，
但它是唯一一组「同卡、同数据、同代码、仅链路不同」的对照臂，因此 §3 与 §9 使用它的**比值**而非绝对值。

## 2. A 侧：换卡后 ×8 / 225 W 的三个数字

### 2.1 档位扫描 → 最小可行档是 8，不是配置默认的 20

每档 16 步，稳态取最后 4 步 [本项目实测]：

| swap | 状态 | rc | 稳态 s/step | alloc MiB | reserved MiB | 全卡 max MiB | 墙钟 s |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 20（首次） | **contaminated**（被 B 侧进程污染，09:56–09:57） | 0 | 5.8500 | 6400.0 | 6558.0 | 9769 | 223.5 |
| 20（干净复跑） | ok | 0 | **5.8430** | 6400.0 | 6558.0 | 6919 | 136.4 |
| 16 | ok | 0 | 4.7020 | 7264.1 | 7418.0 | 7779 | 117.8 |
| 12 | ok | 0 | 3.5535 | 8128.1 | 8278.0 | 8639 | 99.5 |
| **8** | ok | 0 | **2.4173** | 8992.2 | 9138.0 | 9499 | 82.2 |
| 4 | **OOM** | 1 | — | None | None | 9773 | 43.5 |
| 0 | **OOM** | 1 | — | None | None | 9777 | 20.7 |

- 最小可行档 = **8**。swap=4 与 swap=0 分别在全卡 9773 / 9777 MiB 撞死（torch 可用 9788 MiB）。
- swap=8 时全卡峰值 9499 MiB，离 9788 MiB 只剩 **289 MiB**，离标称 10240 MiB 只剩 741 MiB ——
  **没有余量可言**，这也是本轮必须先扫档再测的原因（protocol.md §0.2 的预判成立）。
- 每档省下的显存 = `(8992.2 − 6400.0) / 12 = 216.02 MiB/块` [算术推导]，与 DiT 单 block 权重
  `113,246,208 参数 × 2 B = 216.0 MiB` **逐字节吻合**。
- 非权重足迹在四个档位上恒定 [算术推导]：`8992.2 − ((42−8)×216 + 621.7) = 1026.5 MiB`，
  `6400.0 − ((42−20)×216 + 621.7) = 1026.3 MiB` ⇒ swap 档只改常驻权重、激活足迹不变，
  因此拟合必然是严格线性。
- 干净拟合（4 点，20 档取干净复跑）：**t ≈ 0.1300 s + 0.28564 s/块 × swap**，
  四档残差 +0.09% / −0.12% / +0.04% / 0.00% [算术推导，拟合输入为上文四个档位的实测步时]。

### 2.2 swap=20（t512 配置默认值）在这张卡上贵多少

| 量 | swap=8（最小可行档） | swap=20（配置默认值） | 比值 |
| --- | --- | --- | --- |
| mean s/step | **2.4181** | **5.8460** | **2.4176×** |
| std / min / max | 0.0098 / 2.409 / 2.462 | 0.0110 / 5.838 / 5.892 | — |
| images/s | 0.41354 | 0.17106 | 2.4175× |
| peak alloc / reserved / 全卡 MiB | 8992.2 / 9138.0 / 9499 | 6400.0 / 6558.0 / 6919 | 0.712 / 0.718 / 0.728 |
| 进程墙钟 s | 120.3 | 229.8 | 1.911× |

- 代价 = `+3.4279 s/step = 12 × 0.28564` [算术推导]，与拟合斜率逐位自洽。
- 折算 [算术推导]：每 1000 步多花 **57.1 分钟**（3427.9 s）；反过来说，跑 1000 步 swap=20 的 5846 s，用 swap=8 能跑 **2418 步**。
- 结论：**默认值 20 在这张卡上是纯浪费**——它换来 2592 MiB 的闲置显存（6400 对 8992 MiB），
  本机没有任何东西需要这份余量，代价却是 2.42× 的时间。
  t512 方法配置若要在这类 10 GB 卡上生产，必须把 swap 从 20 降到实测最小可行档。

## 3. 链路 ×4 → ×8 到底换来了多少（问题 2）

同卡、同数据、同代码、同 swap 语义，只改链路与功耗墙（Gen1×4/120 W → Gen1×8/225 W）[本项目实测]：

| 量 | ×4 / 120 W（run-A2） | ×8 / 225 W（run-A3） | 比值 | 降幅 |
| --- | --- | --- | --- | --- |
| swap 斜率 | 559.51 ms/块 | **285.64 ms/块** | **1.9588** | **−48.95%** |
| 截距 | 0.1414 s | 0.1300 s | 1.0877 | −8.06% |
| swap=8 稳态 | 4.6175 s | **2.4173 s** | 1.9103 | **−47.65%** |
| swap=20 稳态 | 11.3320 s | **5.8430 s** | 1.9394 | **−48.44%** |
| swap=8 正式（20 步 × 3） | 4.6317 s | **2.4181 s** | 1.9154 | −47.79% |
| swap=20 正式 | 11.3443 s | **5.8460 s** | 1.9406 | −48.47% |
| swap=8 的 DMA 占比 | 96.9% | 94.5% | — | — |
| swap=20 的 DMA 占比 | 98.7% | 97.8% | — | — |

> 表中「斜率」「截距」是对各自四个档位实测步时做最小二乘得到的拟合值，「比值」「降幅」「DMA 占比」是算术推导；两列 s/step 与显存是实测。

**是否等于 2× 带宽？——不等于 2.000，但等于实测带宽比。**

| 量 | ×4 | ×8 | 比值 |
| --- | --- | --- | --- |
| H2D 实测 | 0.755 GB/s | 1.476 GB/s | **1.9550** |
| D2H 实测 | 0.777 GB/s | 1.559 GB/s | **2.0064** |
| **swap 斜率比（实测）** | — | — | **1.9588** |

- 斜率比 1.9588 落在 H2D 比 1.9550 与 D2H 比 2.0064 之间，**离 H2D 比只差 0.19%**
  ⇒ 斜率就是「每块 453 MB 的 H2D 时间」。（每块 216 MiB = 226.5 MB；一步之内 forward 与 backward
  各把该块搬进一次，所以每块 453 MB，而全程不产生 D2H —— 退役块的显存被下一块复用。见 §5。）
- 逐字节核对 [算术推导]：`453 MB / 0.755 GB/s = 600.0 ms`，`453 MB / 1.476 GB/s = 306.9 ms`；
  实测 559.5 / 285.6 ms ⇒ **搬运效率 93.25% / 93.07%**，两代几乎同一个数。
  这说明斜率是一个**只由字节数和链路带宽决定的常数**，与卡、幅面、功耗墙无关（§9 会用到）。
- 相对「理想 2.000×」的缺口 [算术推导]：理想斜率 = 559.51 / 2 = 279.75 ms/块，
  swap=8 应得 `0.1414 + 8 × 0.27975 = 2.3794 s`，实测 2.4173 s ⇒ **比理想 2× 差 1.6%**；
  swap=20 同理：`0.1300 + 20 × 0.279755 = 5.7251 s`，实测 5.8430 s ⇒ **差 2.1%（+2.06%）**（同一理想斜率算法）。
  **没有 8% 级异常**：所谓「没吃到满 2×」的全部来源就是
  H2D 只涨了 1.955×（不是 2.000×），加上截距不随链路缩放。
- 换车道的账：`swap=8` 从 4.6175 → 2.4173 s，**省 2.2002 s/step（−47.65%）**；
  若同时把默认档 20 改成最小可行档 8，两件事叠加是 11.3443 → 2.4181 s，**−78.7%**。
  这是本轮最大的单笔收益，且**零风险、零代码改动**（只改一个已有配置键）。

### 4.2 必须随数字一起引用的三条 caveat

1. **这是「B 在 sm75 上能跑起来的形态」，不是 B 的设计性能。** 14 个算子全部钉到纯 torch：
   DiT 原语 7 个（rms_norm / rms_norm_mod / qk_norm_rope / attention_varlen / situ_glu / gated_residual / token_mse）
   → eager；fused 3 个（linear_qk_rope / linear_situ / linear_gated_residual）→ SKIPPED(composed)；
   text-encoder 5 个 → eager 且 pinned=True；lycoris → torch。
   硬证据是 `run-B3/preflight_bind.log` 的末行 `PREFLIGHT OK: every op binds to a pure-torch implementation`，
   而且 `run_B3.sh` 里有 `grep -q 'PREFLIGHT OK' || exit 1` 的**门禁**，不是口头声明。
2. **39/60 步的 optimizer 更新被跳过**（§4.3），因此 12.0330 s/step 对这些步不含 AdamW。
   偏置上界 [算术推导]：A 侧 AdamW 探针在同等规模（33,030,144 参数）测得 GPU 常驻 5.7 ms、
   CPU 侧（被跳过的更新真正走的路径）**150–165 ms** —— 三处独立测量 164.5 / 157.3 / 153.7 ms 落在 ±7%，
   落盘输出见 `run-A/adamw_cost_probe.out`（t21 补测，均值 153.7 ms）；
   代入 B 的 12.033 s ⇒ **0.05% – 1.37%**（若换成 A 旧卡 5.8458 s/步 的分母则为 2.6%–2.8%，与探针原始输出同口径）。
   即 12.0330 s/step 相对健康训练最多乐观 1.4%（典型 0.05%），**被跳过的更新占步时 ≤2.8%（按任一坐标轴）**。
3. **torch 版本不同**（A 2.12.0+cu130 / B 2.13.0+cu130，B 的 pyproject 钉 >=2.13）。

### 4.3 必报的第五列：有效更新步数

## 5. 为什么 B 慢 4.98×：两侧都只是 PCIe 字节数（问题 3 的机制）

B 的 `metrics.jsonl` 直接记了每步搬运字节（A 侧没有这个字段），这是本节的关键证据：

| 量 | A（swap=8） | B（MEMORY_PROFILE=low） | 比值 |
| --- | --- | --- | --- |
| 每步 H2D 字节 | 8 × 453 MB = **3.624 GB** [算术推导] | **18.6458 GB** [本项目实测，三次相同] | **5.145** |
| 每步 D2H 字节 | 未计（A 侧无该计数器；进来的块复用退役块存储，不产生 D2H 流） | **1.4324 GB** [本项目实测] | — |
| 每步墙钟 | 2.4181 s | 12.0330 s | **4.976** |
| 有效 H2D 带宽 = 字节 / 墙钟 | **1.4987 GB/s** | **1.5496 GB/s** | 1.034 |
| 扣掉 A 的截距后 | 3.624 / (2.4181 − 0.1300) = **1.5838 GB/s** | 18.6458 / 12.0330 = 1.5496 GB/s | 1.022 |

**读法**：字节比 5.145 与步时比 4.976 相差只有 3.4%，而这个 3.4% 正好是两侧有效带宽之比
（1.5496 / 1.4987 = 1.034），也就是 A 那段 0.13 s 的非搬运截距。
换句话说：**两侧步时都是「每步搬多少字节 ÷ 这条链路多快」，4.98× 的倍数就是字节的倍数。**

三条交叉验证：

1. B 每步 18.6458 GB H2D 按链路 1.476 GB/s 算需要 **12.63 s**，已经超过实测的 **12.033 s**
   ⇒ B 的步时被 H2D 完全封顶（余下约 0.6 s 由重叠吸收，实际流式带宽略高于单次打点值）。
   [算术推导] `18.6458 / 1.476 = 12.63 s > 12.0330 s`
2. B 每步字节折算成 block-slot：`18.6458 GB / 453 MB = 41.16`（或单向 `82.32` 个 226.5 MB 拷贝）
   [算术推导]。42 层 DiT ⇒ **B 在 low 档下几乎每步把整个模型搬一遍**
   （该档 `stream=ring`、`stream_resident=4`、`act_offload=True`，激活 offload 也计在这 18.6 GB 里）。
   而 A 的 swap=8 只搬 8 块。**这就是 5× 的全部来源。**
3. 把 B 的 18.6458 GB 放回 ×4 链路：`18.6458 / 0.755 = 24.70 s`，与 run-B2 在 ×4/120 W 上
   观测到的约 **23 s/step** 同量级 ⇒ 同一份字节数、同一把尺子。

**这条结论比数字本身更重要**：在本机（10 GB 显存 + Gen1×8）这个组合下，B 的绑定约束是**搬运字节**，
不是算子吞吐。所以：

- 即便 B 的 kernel 层 100% 可用，它也拿不到收益——瓶颈不在这里；
- 反过来说，**全 eager 降级在本机对步时的代价近似为零**（已被 DMA 完全掩盖）。
  这**不能**读成「eager 不慢」：它只是被链路掩盖了。链路再快一档（世代 2a 的 ×16、3.09 GB/s 环境），
  B 的 18.6 GB 只需约 6.0 s，此时 eager 的算子开销就会暴露。
  §8 的 1024 档与 4096-token 字幕正是这种情况。

## 6. B 的 NaN 病象为什么与 A 卡上的不同（问题 4）

### 6.1 两种病象对照（不是同一件事，不能互相解释）

| 维度 | 世代 2b 那张卡（GPU-46c7d0db，run-A）上的 A 侧 | 本轮 B 侧（GPU-bfda6d91） |
| --- | --- | --- |
| 首个 NaN 步 | **第 1 步 forward 后即 NaN**（progress 事件 global_step=1 已是 NaN） | 第 1 步起 NaN，但**第 5 步就恢复有限** |
| 分布 | 16/16 步全 NaN，无一步有限 | 23 步里 16 步 NaN、7 步有限，**交替出现** |
| 能否自恢复 | **不能**。NaN 落在权重/激活里就自我维持 | **能**。NaN 步被 DynamicScaler 跳过，权重不被污染，下一步可回归有限 |
| 有效更新 | **0 / 32**（GradScaler 每步 found_inf） | **21 / 60**（35%） |
| 参数是否动过 | **没动**。r1/r2/r3 与 16 步诊断跑的 504 个张量**逐位相同**，max_abs_diff = 0 | 动过（有限步落地） |
| 换 fp32 能否消除 | **不能**（`--mixed_precision no` 仍 NaN，步时 19.82 s） | 未测（B 侧 fp32 会撑爆 10 GB） |
| 换卡后是否复现 | **不复现**：同代码换到世代 3 的卡上 32/32 步全有限、四次跑 adapter 互不相同 | — |
| 判定 | **那张卡的硬件故障表现**，不是 A 侧实现的固有行为 | **实现内的确定性数值越界**，与硬件无关（三次冷启动逐位相同） |

关键差别只有一句话：
**A 卡那次是「NaN 一进去就出不来」（无跳过机制的净效应 + 硬件异常）；
B 这次是「NaN 能被跳过所以能出来」（B 自带跨 rank 一致的 found_inf 跳过 + 逐 step 记账）。**
两者的共同点是都**没有定位到根因**，区别是 B 的病象自带记账（`nonfinite_steps` / `nonfinite_params` / `loss_scale`），
而 A 侧世代 2b 那次的日志里一条 GradScaler 记录都没有——这也是 A 侧当时只能靠「参数逐位不变」倒推的原因。

### 6.2 FP16_FIX 的四种模式解决了没有：**没有一种解决**

| 模式 | 做了什么 | 源码位置 | 本轮 / 前轮战绩 |
| --- | --- | --- | --- |
| none | 不施加；fp16 且权重不带 fold 时**配置直接被拒** | B `fp16fix.py:108-116`、`:184-190` | 无法测（配置层拒绝），非成功 |
| weights | 把 c / s_attn / s_ffn **折进权重** | B `fp16fix.py:122-126` | 未测，且改权重后与 A 侧可比性丧失 |
| online | 权重不动，运行期施加 gate 乘子 + 重设 norm eps + 残差比例 | B `fp16fix.py:127-134`、`:43-61` | **已试，失败**：run-B2 全 eager 14 步里 10 步 NaN，scale 32768→64 |
| **fp32_residual** | 残差流整个 fp32，norm 输出 cast 回计算 dtype | B `fp16fix.py:135-136` | **本轮已试，失败**：13/20 步 NaN，scale 从 init 2^16 连续回退到地板 1.0 |

为什么 fp32_residual 不管用：它只改**残差流的存储 dtype**（`StreamConfig(stream_dtype=fp32)`），
**各算子内部仍按 fp16 计算再 cast 回去**。越界发生在算子内部，改存储救不了。
另外 `c = 1/16` 那套常数是 B 文档专门给 **base（stream 峰值 6.2e4）** 的，本机加载的是 **SFT** 权重，
照抄等于口径借用——这也是本轮选 `fp32_residual`（不依赖任何常数）而不是 `online` 的原因。

### 6.3 下一档是什么（已定位、未测）

`online` + `choose_factors(probe, target=2**12)`（B `fp16fix.py:202-218`）：按实测激活峰值取 2 的幂作为
per-block 的 `c / s_attn / s_ffn`，而不是照抄 base 的 1/16。这是唯一还没试过的一档，
且它需要一次额外的 probe 前向，会在 10 GB 上带来显存与时间成本。

**在它试完之前，「B 侧能在 sm75 上训练 MOSS-Image」这句话不成立。**

### 7.2 为什么这不是「配置错了」，而是结构性的

1. **B 把 TileLang 当 sm70/sm75 的首选张量核后端**：B `backends/tilelang/__init__.py:1`

2. **在 sm75 上它是唯一非 eager 的路**：triton 版同一算子要求 `min_sm=80`
   （B `backends/triton/textenc/attention.py:128`），所以 `attention_varlen_causal` 在 sm75 上

3. **同一套后端承载 DiT 全部 block 算子**：B `backends/tilelang/blocks/_blockops.py:29`（min_sm=70）、

## 8. 这些数字能不能外推到 1024 档（问题 6）

### 8.1 能外推的只有一条：每块 285.6 ms

`285.64 ms/块 = 453 MB / 1.476 GB/s × 0.9307` [算术推导] 是**字节数函数**：
DiT 每块 216 MiB 与幅面无关，所以**这条常数原样适用于 1024 档**。

### 8.2 不能外推「512 是 DMA 主导」——而且方向与直觉相反

仓库里已有 ×16 时期（世代 2a，GPU-46c7d0db，3.09 GB/s）的同型号卡、同族配置档位热测
（`blocks_to_swap=20`、BF16 transfer、foreach restore、full checkpoint、compile 关，与本轮 A 侧配置同族），可以直接检验：

| 行 | 图像 token | swap | 后 9 步 s/步 | 每步 DMA 下限 [算术推导] | DMA 占比 | 判读 |
| --- | --- | --- | --- | --- | --- | --- |
| 512-short | 1064 | 20 | **3.036** | 20 × 453 MB / 3.09 GB/s = **2.93 s** | 96.5% | **DMA 主导** |
| 1024-short | 4200 | 20 | **5.666** | 同上 = **2.93 s** | 51.7% | **计算主导** |
| 1024-short-int8 | 4200 | 20 | **5.822** | 传输 dtype 由 2 B 降为 1 B，名义减半 ⇒ **1.47 s** | 25.2% | 计算主导 |

数据来源：`docs/findings/moss_image_tier_hot_50hx_20261018.md` §2（世代 2a / ×16）。
3.09 GB/s 是世代 2a（×16）实测的拷贝天花板，取 3.14 或 3.16 GB/s 只会让 DMA 下限在 2.87–2.93 s 之间移动，
不改变任何一行的判读（512-short 仍是 95% 以上，1024-short 仍在 50% 上下）。
本表用的是**非配对行**的 5.666 s/步；出处文自己配对的那一行是 **5.688 s**（+2.4%），
与本表算出的 +2.8% 方向一致，换成 5.688 也不改变任何判读。

**最硬的一条是最后两行**：int8 传输把每步搬运字节**名义减半**（9.06 → 4.53 GB，DMA 下限 2.93 → 1.47 s），
1024-short 的步时却从 5.666 变成 5.822 s（**+2.8%，噪声级**）。
搬运量砍一半一点速度都没换来 ⇒ **1024 档由计算而不是搬运决定**。

⇒ 因此正确的说法是：

- 「512 幅面下步时 = 总 DMA」这条**只对 512 档（本次实测的这一档）成立**；
- 分辨率越高越**偏离** DMA 主导（计算按面积涨、每块 DMA 不变），1024/4200-token 已经是计算主导；
- 所以不能把 2.4181 s/step 乘个系数当 1024 的预测，也**不能**说「反正 DMA 主导，幅面影响被淹没」。
  这句话在 512 档成立，在 1024 档恰恰相反。

### 8.3 1024 档在本卡（×8 / 225 W）上是多少：**N/A，必须实测**

只能说清两件事，都不能给数：

1. 1024 档的 swap 最小可行档必须重扫。按世代 2a（×16）时期的记录，1024-short 在 swap=20 下
   alloc 7.90 GiB / 全卡 8619 MiB，而本轮 512@swap=20 只有 alloc 6.25 GiB / 全卡 6919 MiB
   ⇒ 1024 的激活足迹多约 1.65 GiB，本卡（9788 MiB 可用）大概率仍需 swap ≈ 16–20 档。
   **这是估算，不是实测，不得写进任何结论表。**
2. 该档步时将是 `max(S × 285.6 ms, 1024 的计算时间)`，其中计算时间必须实测
   （世代 2a / ×16 实测约 5.67 s，但那是 fp16 / 225 W / 4200 token 的特定点，不能移植到 ×8 档）。

**结论：本次数字无法外推到 1024 档。** 要 1024 的数，就得照本轮协议在 ×8 上重扫档 + 重量一次。

### 9.3 对既有结论的升级（只回引，不改原文）

`docs/findings/moss_vs_kohakumoss_trainer_ab_20261019.md` 的 §7-4 把「11.3386 与 2.9312 差 3.87×」
列为**未验证声明第 4 条**，判定为「最可能为另一块物理卡 + ×4 链路，属推断」，并给了三条佐证。
本轮实测把它从推断升到结论，但**纠正其中一条**：

| §7-4 的说法 | 本轮修正 |
| --- | --- |
| 11.3386 是「另一块物理卡」 | **错**。11.3386 所在 run 的 `environment.json` / `command.json` / `result.json` 的 `gpu_uuid` 与**本轮在机 GPU 完全相同**（GPU-bfda6d91-…）。当时（10-19）在机的是 GPU-46c7d0db，所以「两块不同的物理卡」在**那一刻**成立；今天那张 GPU-bfda6d91 被重新装回来了——卡没换，是链路换了。 |
| 差异来自 ×4 链路、不是口径差异 | **对，且现在有实测**：同一张卡 ×4 的 swap20 = 11.3443 s，与 11.3386 差 0.05%；同卡 ×8 = 5.8460 s，比值 1.9395 ≈ 实测斜率比 1.9588。 |
| ③ 算术自洽 0.799 GB/s ≈ ×4 | **对**，本轮独立复核：`9.06 GB / 11.3386 s = 0.799 GB/s`。 |
| 3.87× 缺口 | 完全由链路解释：`3.09（世代 2a / ×16）/ 0.799（世代 1 / ×4）= 3.867`，与实测比值 3.868 相差 0.03%，**没有残差留给另一块卡，也不需要。** |

⇒ §7-4 那条「256×256 两处 A 侧记录不可比」的结论**方向正确、归因需改**：
不是「另一块卡 + ×4」，而是「**同一块卡 + 不同的链路**」。这个修正让结论更强，
因为它去掉了一个无法证伪的假设（换了卡），只留下一个可以逐次实测的量（链路带宽）。

## 11. 未验证与风险声明

1. **B 侧性能数字只在「全 eager、零张量核」形态下成立**，且 39/60 步没做 optimizer 更新（偏置上界 1.4%）。不得引用为 B 的设计性能。
2. **B 的 NaN 根因未定位。** 四种 FP16_FIX 模式里两种不可用、两种实测失败；剩下的 `online + choose_factors(probe)` 未试。**B 目前不具备可长训的数值前提。**
3. **A 侧 NaN（世代 2b 那张卡）的根因同样未定位**，只确认换卡后不复现，判定为那张卡的硬件故障表现。2026-10-17 A/B 那次 fp16 臂的 Xid 31（MMU Fault）与本轮的 Xid 13/154 是否同源，**没有证据，不做判定**。
4. **B 的 18.6458 GB 是 B 自己的计数器读数**，包含 `act_offload=True` 的激活流量；本报告未把它拆成权重流 + 激活流（B 未提供该粒度字段）。因此 §5 的 41.16 block-slot 只是量级核对，不是「B 每步搬 41.16 个 DiT 块」的断言。
5. **×8 → ×16 的收益未在本轮实测**（本轮链路是 ×8）。§8 里的 ×16 数字全部转引自 `moss_image_tier_hot_50hx_20261018.md` 的世代（世代 2a / ×16），只用于「是否 DMA 主导」的结构性判断。
6. **1024 档在本卡的任何数字都不给**（§8.3）。要数就重量。
7. **质量 / 收敛一律未做**：两侧都没有画质对照基线，本轮所有结论都是吞吐与显存。
8. **B 的 torch 版本比 A 高一个小版本**（2.13 vs 2.12），未做同版本交叉验证。
9. **swap=4 / swap=0 的 OOM 原文未逐行摘录**：`sweep.swap4.log` / `sweep.swap0.log` 保留了日志，本报告只引 rc=1 与全卡峰值 9773 / 9777 MiB。
10. **A 侧 Arm-2（在线编码对齐）仍为 N/A**：MOSS 族契约硬性要求盘上缓存（`moss_compat.py:70-74`），本轮未改变该结论。
